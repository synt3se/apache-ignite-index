# Заметки реализации ядра векторного индекса

Короткие ADR и отклонения от спецификации (`ANALYSIS-AND-ROADMAP.md`, §7) с причинами.
Ветка: `feature/vector-index-core`. Каталог `docs/` в `.gitignore`; этот файл добавлен в git
явно (`git add -f`), остальные документы каталога по-прежнему локальные.

## ADR-1. Persistent map для слоёв дельты — PCollections 5.0.0

**Контекст.** §7.3: `apply` публикует новое состояние за короткий замок писателей; полное
копирование слоя на каждую запись недопустимо, нужно структурное разделение.

**Решение.** `org.pcollections:pcollections:5.0.0` (MIT, 73 КБ, без зависимостей,
байткод Java 9 — проверен `javap`). Используется `HashTreePMap` за внутренним классом
`core.LayerMap` с операциями `get`, `plus`, `size`, `forEach`. Удаление из карты не нужно:
удаление записи — tombstone, слои отбрасываются целиком при публикации.

**Альтернативы.** Своя HAMT — отдельная задача корректности и производительности, не
связанная с векторным поиском (отклонено на ревью плана). Vavr — слишком тяжёлая
зависимость. Paguro — последний релиз в 2022.

**Последствия.** `HashTreePMap` — сбалансированное дерево по хэшу: `plus` копирует
~log₂n узлов. Порядок обхода детерминирован для одинакового содержимого. Замена
библиотеки — один класс; делать после измерения allocation rate (§7.8).

## ADR-2. Ревизия базы закрывает пробел §7.5 при повторной сверке

**Контекст.** Буквальная публикация скана `{scanBase, [], active}` для уже работающего
runtime оставляет в `active` записи, применённые до старта скана. Если следующее событие
ключа потеряно (именно поэтому и запрошена сверка), старая запись active перекрывает
прочитанное сканом значение, а тикет сверки уже израсходован — устаревшее значение навсегда
(дефект класса К2).

**Решение (согласовано на ревью плана).** У базы есть ревизия: для сборки — ревизия захвата,
для скана — ревизия его старта. Запись слоя действует, только если её ревизия больше ревизии
базы. Ревизии в стеке слоёв убывают сверху вниз, поэтому достаточно посмотреть верхнюю запись
ключа. Один резолвер (`State.resolve`) используют поиск, маски, `get`, `forEachLive`,
дедупликация, `liveCount` и материализация входа сборки.

**Следствия.**
- Пока скан открыт, `capture` запрещён: ревизия базы монотонна, публикация скана не
  отклоняется из-за сборки, начатой после его старта. Сборка, захваченная до скана, может
  завершиться в любом порядке со сканом: раньше — публикуется (ревизия захвата ≤ старта
  скана), позже — отклоняется по идентичности базы.
- Пока скан открыт, дедупликация (`UNCHANGED`) отключена: сравнивать надо с будущей базой
  скана, а не с текущим видом. Пример: в старой базе `k=v1`, скан прочитал `v0`, источник
  вернулся к `v1` — без записи в active скан опубликовал бы устаревшее `v0`.
- Frozen-слои при публикации скана отбрасываются: все их записи не новее старта скана.
- Перекрытые базой записи active остаются физически до следующей сборки (учитываются в
  `deltaEntries`, но не в логическом содержимом).

## ADR-3. Точный `liveCount` при публикации скана без большого прохода под замком

Пока скан открыт, `apply` добавляет ключ в неизменяемый журнал `WriteLog` (O(1)). Публикация:
1. вне замка строит базу скана и по снимку состояния считает
   `|скан| + Σ_{k∈журнал} (живо(active[k]) − есть_в_скане(k))`;
2. под замком досчитывает только ключи, записанные после снимка (префикс журнала до узла
   снимка по идентичности).

Проверено детерминированно (запись в окне «снимок → замок» через `hashCode` ключа) и
нагрузочно (параллельный писатель), против полного пересчёта.

## ADR-4. Жизненный цикл скана и сборки

- Действует одна `ScanSession`: новый `beginScan` вытесняет прежнюю. Публикация и отмена
  сверяют идентичность сессии; поздний `close()` вытесненной сессии ничего не трогает.
- `BuildToken` удерживает захваченную базу (счётчик ссылок) до `close()` в любом исходе;
  `publish`, `buildFailed`, `abandonBuild` закрывают токен сами.
- `BuildService` вызывает `capture` в потоке сборки: отказ executor — захвата не было,
  освобождать нечего, повтор через `DelayedExecutor`. Ошибка — `buildFailed` (данные и
  frozen сохраняются, BUILDING снимается, повтор по `Backoff`); `CancellationException` —
  `abandonBuild` без счёта ошибки; `Error` фиксируется и пробрасывается.
- Адаптер ставит скан в очередь по экземпляру runtime, а не по номеру партиции: задание
  прежнего эпизода (партиция ушла и вернулась, `clearAll`) не мешает первоначальному скану
  нового и завершается само. Страховка: сверка заново ставит скан runtime, который остался в
  `LOADING` без задания в очереди (например, пул отклонил первоначальный скан).

## ADR-5. Неизменяемость векторов

Публичное чтение (`ReadView.get`, `forEachLive`) отдаёт копии. SPI алгоритма
(`FrozenVectorView.vector`, запрос в `SearchStructure.search`) — доверенный доступ без копий:
только чтение, структура может удерживать массивы, пока открыта. В Java это не обеспечить без
копирования, поэтому контрактный набор проверяет неизменность векторов и запроса после сборки
и поисков для каждого алгоритма.

## ADR-6. Контракт расстояния

COSINE: копия нормализуется при приёме, расстояние `1 − dot` в double; нулевая норма остаётся
нулём → расстояние 1.0 (контракт `zeroNormProducesFiniteDistance` сохранён). JVector строит
граф с DOT_PRODUCT для COSINE и EUCLIDEAN для SQUARED_L2; его оценки наружу не выходят —
кандидаты переранжируются точным расстоянием ядра.

## ADR-7. Бюджет и добор

`Budget` (монотонный, локальный для JVM; между узлами — только остаток) входит в
`SearchParams` и SPI. Поиск по виду идёт этапами: подготовка frozen → active → frozen → база
(ANN, повтор с `widen` — JVector: ef×2, точный fallback) или точный перебор базы. Каждый этап
начинается только в бюджете: циклы проверяют его перед первым элементом и далее раз в 1024
элемента; перед базой — явная проверка в ядре, независимо от проверки внутри алгоритма. Начатый
этап выходит за бюджет не больше чем на интервал проверки или на один обход графа JVector —
обход неделим, его стоимость ограничена `ef`.

Разрешение frozen-слоёв (действующие записи, маска базы) прогревается в `capture` вне замка, в
потоке сборки. Поиск, попавший в окно до прогрева, готовит разрешение в своём бюджете: прерванная
подготовка ничего не кэширует, завершённая кэшируется для следующих запросов.

Исчерпание бюджета — `BUDGET_EXHAUSTED` без результатов: частичная партиция не попадает в
покрытие. Недобор ANN без бюджета на fallback — `annUnderfilled` (качество, не покрытие).

## ADR-8. Координатор: назначение партиций

Назначение «партиция → primary-владелец» фиксируется в начале запроса по affinity
координатора; узел ищет только по своим партициям. Покрытие — партиции, о которых сообщил
назначенный узел; сообщения о неназначенных игнорируются, неупомянутые — `NOT_REPORTED`.
Двойной учёт исключён по построению (правило «большая версия топологии» отклонено на ревью).
Повтор ключа — нарушение назначения: считается в `duplicateKeys`; одно вхождение (с меньшим
расстоянием) остаётся только чтобы не занимать два слота — это не выбор версии.

## ADR-9. Модули и тестовые средства

JVector — отдельный модуль `vector-index-jvector`: сборка сама гарантирует, что в ядре нет
JVector. Контрактный набор — в обычном jar `vector-index-testkit` (scope=test у потребителей),
а не в test-jar: так соседние модули получают его из реактора на фазе `test` без `install`
(проверено `mvn -pl vector-index-node -am clean test`).

## ADR-10. `NodeSearchRequest` — обычный класс

Запрос узлу уходит по сети внутри compute job и маршаллируется Ignite. Бинарный маршаллер
Ignite 2 работает с полями через Unsafe, что для record не гарантировано; поэтому обычный
`Serializable`-класс. Проверено распределённым IT через настоящие compute job.

## ADR-11. Определения индексов и их отпечаток (этап C)

Определение — `VectorIndexConfiguration` в XML узла (`name`, `cacheName`, `field`, `dimension`,
`metric`, `algorithm`, `jvectorProperties`), статическое и одинаковое на узлах (§7.1). Без списка
`indexes` действует прежняя конфигурация: индекс `vectors` по полю `vector`, COSINE.
Каталога нет, поэтому совместимость между узлами проверяется на каждом запросе: координатор
отправляет отпечаток своего определения (SHA-256 всего, что меняет смысл ответа: кэш, поле,
размерность, метрика, алгоритм и его параметры построения и поиска). Узел с другим определением
отвечает `DEFINITION_MISMATCH` по своим партициям — такой ответ не бывает `COMPLETE`, а
готовность показывает узел в `mismatchedNodes`. Пороги пересборки в отпечаток не входят: это
настройка эксплуатации, а не смысл ответа.

## ADR-12. Реестр индексов узла и выгрузка

`NodeIndexRegistry` в `nodeLocalMap` экземпляра Ignite: настроенные определения, загруженные
адаптеры и **одни на узел** пулы применения, сканов, поиска и сборок (§7.7). Адаптер ресурсами не
владеет. Узел различает три состояния индекса: `LOADED`, `UNLOADED` (настроен, выгружен) и
неизвестный `indexId` — в поиске это `NO_INDEX` и `INDEX_UNLOADED`, в REST — 404 для неизвестного.

`unload` — **выгрузка настроенного индекса без долговечного каталога**: закрываются только его
подписки, периодические задания и runtime (поздние сборки отклоняет ядро); другие индексы того же
кэша и общие пулы не затрагиваются; общие пулы закрывает реестр при остановке сервиса.
Запуск реестра атомарен: если не удалось создать или запустить какой-либо индекс, останавливаются
все созданные адаптеры, включая частично запущенный (его подписки и периодические задания), и
закрываются общие ресурсы; наружу уходит исходная ошибка. После
рестарта узла индекс снова загружается из конфигурации — тогда ответы для его партиций честно
показывают разные состояния узлов. Операция выполняется отдельным вызовом на каждый сервер (без
failover) и возвращает исход по узлам; `confirmed` — только если ответили все серверы топологии и
каждый с допустимым исходом.

## ADR-13. Вектор из поля `BinaryObject`

Адаптер читает кэш через `withKeepBinary()`: вектор — одно поле `BinaryObject`, значение целиком не
десериализуется и класс значения на сервере не нужен. Без поля в определении значение кэша само
должно быть `float[]`. Решение по записи (`SourceValue`): вектор — `upsert`; нет записи или нет
поля — `delete` (не индексируется); поле не `float[]` (или значение не объект с полями) —
исключение из проекции и счётчик `wrongTypeValuesTotal` в готовности. Принимается только FP32.

## ADR-14. Ключи v1: `Long`, `String`, `UUID`

Это классы JDK: ответ проходит compute и тонкий клиент без классов приложения на координаторе и
клиенте. Ключ другого типа (в том числе `BinaryObject` пользовательского типа) не индексируется и
считается в `unsupportedKeysTotal`. В REST ключ передаётся с явным типом
(`{"key": …, "keyType": "LONG|STRING|UUID"}`): JSON не различает строку и UUID, а число может
потерять тип. Поддержка пользовательских ключей потребует отдельного решения о представлении на
проводе (например, бинарная форма) и проверки с разными classpath.

## ADR-15. Статус ответа и строгий режим

`COMPLETE` — заявленный поиск выполнен по всем ожидаемым партициям, назначенные владельцы
ответили, известных пробелов нет, бюджет не исчерпан, повторов ключей нет. Точность ANN и
свежесть относительно всех записей источника — отдельные свойства, статус их не утверждает.
Причины неполноты перечисляются все (`MISSING_PARTITIONS`, `KNOWN_GAP`, `TIMED_OUT`,
`NODE_NO_RESPONSE`, `DUPLICATE_KEYS`); одного сравнения «обработано = ожидалось» недостаточно.
`allowPartial=false` — неполный ответ становится `FAILED` без попаданий, покрытие и причины
сохраняются (REST 503). Ошибки запроса возвращаются в ответе (`UNKNOWN_INDEX` → 404,
`INVALID_REQUEST` → 400), а не исключением: через тонкий клиент тип исключения не сохраняется.

## ADR-16. Гидрация в прикладном слое, бюджет на сервере

Сервис поиска возвращает только ключи и расстояния. Документы демо-кэша читает
`index-vector-server` (`IndexSearchClient` + `DemoHydrator`, перенесён вместе с тестами). Бюджет
начинается на сервере и ограничивает всё: ожидание вызова сервиса через тонкий клиент (прокси с
таймаутом остатка), повтор после отказа координатора (только если остаток есть) и гидрацию.
Остаток передаётся сервису как `timeoutMs`: сам по себе он не ограничил бы блокирующий вызов.

## ADR-17. Готовность — наблюдаемый признак, не барьер

`IndexStatus` классифицирует партиции по назначенному владельцу. `observedReady` = все ожидаемые
партиции `READY` у назначенных владельцев, нет ожидающих сверок, нет выполняющихся применений
(очередь **и** уже работающий обработчик: `pendingApplies` считается от приёма полосой до
завершения), нет сканов, все серверы ответили, загрузили индекс и согласны с определением.
Это не доказательство окончания загрузки: позиция источника неизвестна, событие может быть ещё не
доставлено. Для бенчмарка (этап D) нужен протокол: завершить подтверждённые записи, остановить
писателей, запросить полную сверку и дождаться именно этого прохода на всех ожидаемых партициях при
стабильном назначении; затем при необходимости — оптимизации.

## ADR-18. Метрики: узел и индекс раздельно

Общие ресурсы узла (heap, общая очередь применения, uptime) — `vindex.node.*`, по одному значению на
узел. Метрики индекса — `vindex.index.*` с тегами `node` и `index`, без повторения общих ресурсов.
Прежние гейджи `vindex.node.*` полей индекса сохранены для дашбордов и описывают индекс по
умолчанию (`vectors` или первый настроенный).

## Известные ограничения v1

- Видимость eventual на событиях кэша; позиция источника неизвестна (`SourcePosition.UNKNOWN`).
- Синхронная видимость через `IndexingSpi` — по итогам спайка. Канонический отчёт лежит рядом с
  экспериментами: `spikes/indexing-spi/SPI-SPIKE.md` в отдельной ветке
  `claude/spike-indexing-spi-a8ced4` (её не сливали). Гибрид «SPI + события» нельзя подключать
  простым соединением двух путей. Возможна гонка: обработчик события прочитал v1, SPI синхронно
  применил v2, затем обработчик применил прочитанное v1 — и локальная ревизия даёт старому
  значению новый номер. До подключения нужен единый протокол порядка и тест на реальном runtime.
- Жёсткого memory budget нет: пока сборка отложена или скан открыт, дельта растёт.
- `docker/docker-compose.yml` монтирует `docker/ignite-libs`, поэтому после сборки нужен комплект
  с новыми jar-ами. Сначала `docker/build-ignite-libs.sh` без `--install` — он выводит список
  добавлений и замен. После просмотра: `--install docker/ignite-libs`.

- Пользовательские типы ключей не поддерживаются (ADR-14).
- Готовность — наблюдаемый признак; барьер окончания загрузки для бенчмарка — протокол этапа D
  (ADR-17).
