# Проверки ядра векторного поиска

Тесты сосредоточены в `vector-index-node`: локальные движки, применение изменений
кэша, публикация индекса, распределённый top-k и гидрация. REST, Telegram, gateway,
embedding-сервис и нагрузочные раннеры в этот набор не входят.

## Запуск

Проверенный вариант — JDK 21 и Maven. Проверьте `mvn -version`: Maven использует
`JAVA_HOME`, который может отличаться от `java` в PATH. Текущие Mockito/Byte Buddy
не поддерживают JDK 26 без дополнительных изменений зависимостей.

Из корня репозитория:

```powershell
# Все проверки, включая известные дефекты и локальные интеграционные тесты.
mvn -pl vector-index-node -am clean test

# Проверки без группы известных дефектов.
mvn -pl vector-index-node -am test "-DexcludedGroups=known-issue"

# Только проверки известных дефектов.
mvn -pl vector-index-node -am test "-Dgroups=known-issue"

# Только интеграционные проверки на настоящем Ignite.
mvn -pl vector-index-node -am test "-Dtest=DerivativeIndexIT" "-Dsurefire.failIfNoSpecifiedTests=false"
```

Первый `clean` удаляет старые скомпилированные тесты, исходников которых уже нет.
После него достаточно `test`. `-am` собирает также `vector-index-common`; остальные
сервисы не собираются. При первом запуске Maven загружает зависимости.

Surefire явно включает `*IT`, поэтому интеграционные проверки выполняются уже на
фазе `test`, отдельного запуска Failsafe не требуется. Отчёты последнего запуска:
`vector-index-node/target/surefire-reports/TEST-*.xml` и соседние `.txt`.

## Как читать результат

Тег `known-issue` **не отключает тест** и не превращает дефект в ожидаемый успех.
Проверки утверждают корректное поведение, поэтому полный запуск сейчас завершается
с ненулевым кодом. После исправления реализации соответствующий тест должен стать
зелёным без ослабления утверждений; затем снимите тег, чтобы проверка вошла и в
обычный набор с `excludedGroups`.

Исходный прогон 20.10.2026 на JDK 21 / Ignite 2.17.0 из `pom.xml`:
**62 проверки: 57 прошли, 5 упали, ошибок выполнения и пропусков нет.**
Это число включает параметризованные случаи для двух движков.

| Проблема | Проверка | Исходный результат |
|---|---|---|
| К1: удаление теряется при публикации графа | `JVectorPartitionIndexTest.deletionAfterUpdatedVectorWasCapturedMustSurvivePublication` | Падает: размер возвращается с 2 к 3, удалённый ID снова выдаётся |
| К2: потеря запроса восстановления после overflow во время скана | `PartitionIndexManagerTest.overflowDuringRebuildIsNotForgottenByConcurrentReconcile` | Падает: после reconcile остаётся старый вектор |
| К4: гидрация после исчерпания бюджета | `SearchAggregatorServiceImplTest.doesNotStartHydrationAfterDeadlineIsExhausted` | Падает: вызывается `getAll` после таймаута |
| К4: coverage не соответствует фактическому поиску | `NodeSearchJobCoverageTest.coverageDescribesSearchedPartitionsRatherThanLaterActivation` | Падает: учитывается партиция без обработанного индекса |
| Владение входным массивом в brute force | `BruteForcePartitionIndexTest.addCopiesCallerOwnedArray` | Падает: изменение массива вызывающим кодом меняет сохранённый вектор |

## Что покрыто

- `PartitionVectorIndexContractTest`: общие проверки BruteForce/JVector — пустой
  индекс, k, косинусное расстояние и порядок, update/delete/reinsert/clear,
  копирование данных при build, нулевая норма. Для небольших наборов с полным
  перебором hot-слоя или достаточным числом кандидатов; это не обещание recall=1
  для произвольного ANN-запроса.
- `JVectorPartitionIndexTest`: граф и hot-слой, маскирование старых версий,
  валидация размерности, дедупликация, доступность seed до публикации, обновления,
  удаления и clear во время сборки, доступность читателей.
- `PartitionIndexManagerTest`: чтение актуального значения по событию, повторы,
  удаления и null-вектор, fallback `localPeek → get`, top-k по партициям, смена
  владельца, replay событий во время скана и восстановление после overflow.
- `PartitionStateTest` и `StripedApplierTest`: публикация и replay, доступность
  предыдущего индекса, порядок применения, независимость полос и переполнение.
- `SearchAggregatorServiceImplTest`: глобальный top-k, дедупликация по ID,
  гидрация и её батчи, пропуски удалённых записей, добор кандидатов, отказы и
  таймауты узлов, неполное покрытие даже при наличии k результатов.
- `DerivativeIndexIT`: настоящий двухузловой Ignite — события put/update/remove,
  потеря узла и возврат узла без потерь и дубликатов.

К5 проверяется для текущего управляемого bulk-сценария: pause, clear, записи во
время паузы, resume с полным пересканом. Это не утверждение о будущем контракте
самостоятельного `clear`. К6 закрыт конфигурацией запуска существующих IT.

## Управление конкурентностью и изоляция

К1 воспроизводится защёлкой в тестовом наследнике `JVectorProperties`: сборка
останавливается после захвата исходных данных, затем выполняется удаление.
К2 использует настоящий `StripedApplier` с маленькой очередью, управляемый executor
пересборки и барьер скана. Тесты проверяют итоговый поиск и содержимое, а не наличие
внутреннего флага ошибки. Произвольные задержки для попадания в эти гонки не нужны.

Из-за отсутствия публичных seams используются узкие test-only обращения через
reflection: инъекция зависимостей менеджера и ожидание завершения сборки под её
блокировкой. При будущем рефакторинге соответствующие helpers могут потребовать
адаптации. Production-код для тестирования не изменён.

Интеграционные тесты используют loopback, discovery-порты 37500–37509,
communication-порты 37200–37209 и временные рабочие каталоги. Docker, данные проекта
и внешний кластер не нужны. Число доступных процессоров тестовой JVM ограничено
четырьмя, data region каждого узла — 64 МиБ. Пороговые пересборки маленького набора
отключены в IT; сами гонки публикации проверяются отдельно с барьерами.

## Границы покрытия

Набор пока не проверяет К3 на пути REST/бенчмарков, наблюдаемость К7, совпадение
версий расстояния и metadata, пересечения покрытых партиций между узлами,
распространение отмены до узлов, persistence и транзакционные гарантии. Текущие DTO
не передают версии записей и ID обработанных партиций, необходимые для части этих
контрактов. Это отдельные оставшиеся задачи, а не вывод из зелёных тестов.
